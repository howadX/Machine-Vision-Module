# План ревизии ML-подхода MVM

> Живой документ. Отвечает на вопрос: «мои модели не самые оптимальные — в каком
> порядке это чинить, чтобы по ходу можно было переосмыслять подход, и что из этого
> станет новыми моделями в портфолио».
>
> Опирается на [METHODOLOGY-AUDIT.md](./METHODOLOGY-AUDIT.md) (диагноз) и на 6 живых
> Kaggle-ноутбуков (макеты). Последнее обновление: 2026-07-13.

---

## 0. Три принципа, которые определяют порядок

1. **Сначала измерение, потом оптимизация.** «Чувство, что модель плохая» — не данные.
   Нельзя улучшать то, что не измерено честно. Поэтому Фаза 0 — не модели, а *инфраструктура
   доверия к цифрам*. Это же — сильнейший senior-сигнал в портфолио: «сначала построил
   измерение, потом трогал модели».

2. **Два числа вместо одного.** Каждая метрика докладывается парой: «на невиданных **кадрах**»
   и «на невиданных **людях**» (grouped CV). Разрыв между ними — это и есть скрытая болезнь
   (audit A2/D2: почти везде отсутствует grouped-валидация → метрики завышены на 5–15 п.п.).

3. **Обратная связь важнее плана.** Порядок ниже — не рельсы. Если на Фазе 2 всплывёт, что
   ранний подход в NB1 ошибочен, мы чиним *исходный build-скрипт*, добавляем «What Changed»,
   перезаливаем — и, если затронут production, заводим задачу против MVM. См. «Протокол ревизии».

## Протокол ревизии (что делать, когда нашли ошибку по ходу)

Любая находка проходит один и тот же цикл — это делает исследование самоисправляющимся:

```
находка → воспроизвести (тест/цифра) → классифицировать:
  ├─ косметика/нарратив   → правим _build_nbX.py + What Changed → push
  ├─ метрика завышена     → чиним измерение, публикуем ОБА числа, не прячем падение
  ├─ баг в модели         → golden-тест, фиксящий баг → фикс → регресс-тест
  └─ production-релевантно → задача против mvm/ (Rust), пометка в CLAUDE.md
```

Правило честности: **если исправление роняет метрику — это успех, а не провал.** Падение с
«возможно завышено» до «честно измерено» повышает ценность портфолио.

## Карта: сила / риск / production каждого актива

| Ноутбук | Что это | В production? | Уверенность в качестве | Где болит (audit) |
|---------|---------|:---:|:---:|-------------------|
| NB3b Method-C | 14 фич → RF, поза | ✅ основной | 🟢 высокая | 26 групп мало; RF вбит вручную (C1) |
| NB1 Distillation | CNN→MLP эмоции | ❌ (prod=EmotiEffLib) | 🔴 низкая | teacher-leakage; нет golden-теста; нет калибровки (E3, G3) |
| NB2 PoseVAE | manifold + OOD | ✅ только OOD-gate | 🟡 средняя | data leakage: VAE учился на всех данных (A2, G1.3) |
| NB3 Weak-sup | эвристика→LightGBM | ⚪ бутстрап | 🟡 средняя | потолок = точность эвристики; 15 trials мало (C1) |
| NB0 EmoZid | SVM 2019 | ❌ архив | ⚪ baseline | off-by-one, нет stratification — уже как урок |
| NB4 Teardown | инженерное суждение | — | 🟢 (аргумент) | нужен эмпирический замер, а не только текст |

**Вывод из карты:** самый большой разрыв «ожидание↔качество» — **эмоции (NB1)**. Самый
надёжный быстрый выигрыш — **поза (NB3b)**. Поэтому модельную работу начинаем с NB3b как
«пайп-клинера» (обкатать harness на понятной модели), а затем бьём по самому больному — эмоциям.

## Фаза 0 — Фундамент: инфраструктура честных цифр  ⏱ ~день

Ничего не улучшаем. Строим то, без чего улучшение — гадание. Закрывает F2 аудита
(experiment tracking, data versioning, тесты моделей).

- **0.1 Единый бенч-харнесс** (`bench.py`, шарится всеми ноутбуками): на вход — модель +
  датасет + groups; на выход — таблица `accuracy · balanced_acc · macro-F1 · ECE(калибровка) ·
  latency_CPU · size_KB`, всегда с grouped-CV (μ±σ). Один источник правды для всех сравнений.
- **0.2 Experiment tracking.** W&B (работает на Kaggle через secret; шареные дашборды — плюс
  для рекрутёра). Фолбэк без внешних сервисов: структурный `results/*.json`, коммитим через git.
  Каждый прогон логирует seed, данные (хеш/версия Kaggle-датасета), гиперпараметры, метрики.
- **0.3 Golden-тесты как паттерн.** Обобщить `spike_pose/golden_refs.py` на все production-модели.
  **Приоритет — эмоции**: один известный кадр → EmotiEffLib → эталонный вектор. Именно его
  отсутствие дало багу HWC/NCHW прожить 4 фазы (audit E3). Это защита и research, и production.
- **0.4 Data versioning.** Все derived-датасеты → Kaggle Datasets с хешем (начато:
  `mvm-pose-landmarks`). Модель всегда знает, на какой версии данных обучена.

**Критерий готовности Фазы 0:** любой ноутбук может вызвать `bench()` и получить честную
таблицу; есть golden-тест эмоций, ловящий HWC/NCHW-класс багов.

## Фаза 1 — Честное перепроведение (audit → доказательства)  ⏱ ~день

Прогоняем существующие модели через harness Фазы 0. Цель — превратить «чувство» в карту дыр.

- **1.1** Перемерить **все** модели с grouped-CV, доложить пару чисел (кадры vs люди). Ожидаемо:
  часть метрик падает на 5–15 п.п. — это и есть настоящий baseline (audit G1.1).
- **1.2 Починить data leakage в VAE-пайплайне** (NB2): обучать VAE только на train-фолде, потом
  считать эмбеддинги (audit G1.3). Ожидаемо −3–5 п.п. у классификатора на латенте.
- **1.3 Калибровка.** ECE + reliability-диаграмма для эмоций (EfficientNet vs EmotiEffLib) —
  насколько модель «честна» в вероятностях (audit G3.9). Часто вскрывает overconfidence.
- **1.4** Задокументировать teacher-leakage NB1: HSEmotion учился на AffectNet → soft-метки того
  же датасета оптимистичны (audit G3.10). Честная пометка в ноутбуке.

**Итог Фазы 1:** таблица «заявлено → честно измерено» по всем моделям. Теперь мы *знаем*, а не
*чувствуем*, где чинить. Это же — готовая секция статьи «эволюция junior→senior честно».

## Фаза 2 — Углубление по моделям (порядок по рычагу)

Каждый пункт: *текущее → подозрения → эксперименты → «переосмысление» → production-hook → выхлоп*.

### 2A. Поза / Method-C (NB3b) — пайп-клинер, самый надёжный выигрыш
- **Подозрения:** RF (`n_estimators=120, max_depth=16`) вбит вручную (C1); 26 групп → широкий CI;
  3 класса грубоваты.
- **Эксперименты:** Optuna по RF с grouped-CV (audit G2.6); ablation 14 фич (какие реально
  несут сигнал); расширить данные новыми публичными позами (→ больше групп → уже CI).
- **Переосмысление:** достаточно ли 3 классов для «умного дома»? Нужен ли отдельный класс
  «переходное/падает» — мостик к 2D (темпоральная модель).
- **Production:** обновлённый `pose_rf_forest.bin` → `mvm-posture` (golden-тест уже есть).
- **Выхлоп:** 0.959 → честно подтверждённые/улучшенные цифры; отработанный harness для эмоций.

### 2B. Эмоции / Distillation (NB1) — самый большой разрыв качества
- **Подозрения:** teacher-leakage; нет калибровки; student не в production (prod=EmotiEffLib) —
  почему? нет golden-теста; accuracy на софт-метках ≠ на реальных (audit D1, E3).
- **Эксперименты:** честная grouped-оценка на AffectNet (там есть identity); калибровка +
  temperature scaling; сравнить student vs EmotiEffLib на едином бенче (acc↔latency↔ECE);
  переобучить student с честным teacher’ом / другой температурой дистилляции.
- **Переосмысление (главное!):** правильная ли постановка? Может, эмоции — не 7 независимых
  классов, а **valence/arousal-регрессия** (AffectNet даёт V/A)? Может, per-frame → temporal
  сглаживание? Здесь наиболее вероятно рождение **новой модели** (см. 3B).
- **Production:** если калиброванный student бьёт EmotiEffLib по acc↔latency↔ECE → кандидат в
  `mvm-emotion` (первая полностью «своя» production-модель эмоций).
- **Выхлоп:** сильнейшая история data-centric + честности; потенциально новая prod-модель.

### 2C. Weak supervision (NB3) — замкнуть data-centric петлю
- **Подозрения:** потолок = точность эвристики (~65–75%); 15 Optuna-trials мало (C1).
- **Эксперименты:** active learning — низко-`label_confidence` примеры на ручную разметку →
  дообучение; 50+ trials; измерить «модель обобщает за пределы эвристики или зубрит правило».
- **Переосмысление:** нужен ли LightGBM вообще, если method-C (14 фич) уже лучше? NB3 может стать
  чисто **историей про данные** (как бутстрапнули датасет), а не про классификатор.
- **Выхлоп:** зрелая active-learning петля — редкий и ценный сигнал в резюме.

### 2D. PoseVAE (NB2) — честно переопределить роль
- **После 1.2 (фикс leakage):** VAE — это OOD-gate, а не классификатор. Переписать нарратив
  под честные метрики anomaly/OOD (−log p(z)), few-shot на 5 примерах.
- **Переосмысление:** VAE vs современный OOD (нормализующие потоки / энергетические модели)? Или
  оставить как есть — 48K параметров, в production как gate, «правильный инструмент под задачу».

### 2E. Teardown (NB4) — довести до эмпирики
- Заменить «текстовый аргумент» на **замер**: UMAP identity-эмбеддинга, раскраска по человеку
  (кластеры) vs по эмоции (каша); силуэт-скор. Это единственная модель, где «улучшение» = не
  трогать веса, а доказать тезис цифрой.

## Фаза 3 — Новые модели (расширение портфолио)

Кандидаты, по убыванию ценности (production × новизна × сила для резюме):

### 3A. ⭐ Темпоральный детектор падений (sequence-модель по позе) — топ-приоритет
- **Почему:** URFD — это *временны́е последовательности падений*, а MVM сейчас ловит падения
  эвристическим FSM/anomaly (по памяти — walking-фрагментация ломает fall-anomaly). Обучаемая
  темпоральная модель (маленький TCN/GRU над последовательностью 14 фич method-C) —
  (1) реально нужна production, (2) новизна для портфолио, (3) прямое продолжение NB3b.
- **Данные:** URFD (падения) + Zenodo (статика как negatives) — уже в `landmarks.npz`, нужно
  добавить временну́ю ось. Экспорт в Rust тем же бинарным приёмом.
- **Выхлоп:** новый ноутбук NB5 + возможная prod-замена FSM-эвристики.

### 3B. Калиброванная edge-модель эмоций «сделано правильно»
- Контраст к 2019/2023-попыткам: честный teacher, temperature scaling, ECE-цель, grouped-eval,
  golden-тест. Если побьёт EmotiEffLib по acc↔latency↔ECE — идёт в production (см. 2B).

### 3C. (опц.) Multi-task голова: поза + активность из одних фич
- Одни 14 фич → 2 головы (класс позы + грубая активность). Экономия вычислений, интересный
  инженерный ход. Ниже приоритет — сначала 3A/3B.

## Фаза 4 — Консолидация: production + статья

- Каждое **валидированное** улучшение → PR в `mvm/` (Rust-крейт) или явная пометка «research-only».
- Каждый ноутбук получает «What Changed» с датой и дельтой метрик.
- Материал складывается в **статью на Habr**: MVM (Rust-продукт) + 6→N ноутбуков (траектория
  2019→2026) + честная эволюция методологии (Фаза 1) как главный нарратив.

## Порядок и зависимости (одной картинкой)

```
Ф0 Фундамент (bench + tracking + golden + data-version)   ← делать ПЕРВЫМ
        │
Ф1 Честное перепроведение (два числа, фикс leakage, ECE)
        │
Ф2 ──┬─ 2A Поза/Method-C (пайп-клинер, надёжно) ─────────┐
     ├─ 2B Эмоции (самый большой разрыв) ────────────────┤ находки
     ├─ 2C Weak-sup / active learning                    │ возвращаются
     ├─ 2D VAE (роль OOD)                                 │ в Ф0/Ф1
     └─ 2E Teardown (эмпирика)                            │ (протокол ревизии)
        │                                                 │
Ф3 Новые модели: 3A Fall-TCN ⭐ · 3B эмоции-right · 3C multi-task
        │
Ф4 Production PR + What Changed + статья Habr
```

## Что сделать прямо сейчас (первый шаг)

Начать с **Ф0.1 + Ф0.3-эмоции**: собрать `bench.py` и golden-тест эмоций. Это конвертирует твоё
«чувство» в таблицу за один прогон и сразу защищает production от класса багов HWC/NCHW. Дальше —
Ф1 (перемерить всё честно), и только потом трогаем сами модели, начиная с Method-C.

## Открытые вопросы (решить по ходу)
- W&B или self-hosted JSON-tracking? (внешний сервис vs полная автономность репо)
- Эмоции: классификация 7 классов или V/A-регрессия? (решается в 2B)
- Fall-detection: заменяет FSM или дополняет его как отдельный сигнал? (решается в 3A)
- Порог «идёт в production»: насколько лучше должна быть новая модель, чтобы менять Rust-крейт?
