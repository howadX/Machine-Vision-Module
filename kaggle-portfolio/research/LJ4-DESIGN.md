# LJ4 design — «A camera that never lies: simulating the world for the fusion layer» (15.4)

> Внутренний design-контракт этапа 15.4 (RU). Журнал LJ4 — EN (стандарт портфолио).
> Правило фазы: гипотезы с **заранее названными критериями провала** фиксируются ДО первого числа.
> Линейка не меняется: метрики компонента «Симулятор/FSM» из бенч-протокола (§1) —
> event-precision/recall vs сценарий + anomaly false-alarm rate; паспорт `bench.passport(...)`
> в каждом прогоне, групповой bootstrap CI (N=1000, seed=0).

## Решённые развилки (утверждено 16.07.2026)

- **Вариант A (решение Вадима): Python-лаборатория + Rust-CI.** Temporal-стек над детекторами
  портируется в Python битно к прод-константам (паттерн LJ2-stabilizer/LJ3-tracker):
  `infer_activities` (fusion.rs:365) + `ActivityJournal` (activity.rs) + `AnomalyScorer` (anomaly.rs)
  → `spike_pose/lj4_fusion.py`. Трекер уже портирован (`lj3_tracker.py`, + фикс stale-identity 15.3).
  Сценарии = **данные** (JSON/npz, один источник) → тонкий Rust-runner (`--stub`-класс тестов)
  прогоняет те же файлы через прод-крейты v0.1.0 в CI. Порт победивших изменений — 15.6.
- **Raw activities признаны ситуативными артефактами (директива Вадима 16.07).** Словарь
  `typing/using_mouse/using_phone/holding_drink/reading/watching_tv` — артефакты обучения «на глаз»,
  не результат аудита данных. Следствие: акт S3 — не инвентаризация, а **вход для словаря v2**;
  baseline при этом меряется на битном порте текущего прода (сначала воспроизводим, потом меняем).
- **Количественный аудит требует per-image VRD-аннотаций**: в `oi_meta/` лежит только словарь
  триплетов; дотягиваем `validation-annotations-vrd.csv` (GCS, мал) — считаем размеченные
  ИНСТАНСЫ предикатов, не только словарь. Train-VRD (~3.3M строк) не тянем.
- **Заморозка предыдущих этапов.** `mocap_{views,transitions,tracks}.npz` и их sha256 не трогаем;
  сценарии собираются композицией из существующих артефактов + синтетических объектов, новый
  артефакт — `golden_scenarios.npz` (+ его Kaggle-датасет `mvm-golden-scenarios`, derived-only).

## Крючок (зачем вообще, в одну мысль)

Каждый слой temporal-стека уже промерен изолированно (поза LJ1, переходы LJ2, трекер LJ3), но их
**композицию** — tracker→fusion→FSM→anomaly→journal — до сих пор проверяли только глазами на живой
камере, где истина неизвестна. 15.3 показал цену: фантомные треки рождали ложный `people_together`
и ломали fall-anomaly, и никто не мог сказать «журнал соврал», потому что не было мира, где события
известны by construction. Симулятор — это камера, которая не умеет врать: истинный сценарий задан
декларативно, инжекция идёт ПОСЛЕ детекторов, и любое расхождение журнала со сценарием — дефект
стека, а не «может, так и было».

Ставка 15.4: (1) на чистых данных прод-стек воспроизводит сценарии, (2) под детекторным стрессом
деградация измерима и атрибутируема слою, (3) продовое fall-правило anomaly (standing→lying ≤ 3 с,
**без скорости** — `ANOMALY_FALL_WINDOW_S`) физически не отличает падение от controlled lie-down —
LJ2 E2 уже установил, что разделяет их скорость таза (порог ≳1.13 м/с, AUROC 1.000).

Прод-константы стека (из `activity.rs`/`anomaly.rs`/`fusion.rs`):
FSM `ENTER_DWELL=3`/`EXIT_DWELL=5` (young 8 / old 4, D_MIN=2s, D_TYP=600s), `CONF_LAMBDA=0.7`,
caps 64/256, stitching opt-in; anomaly noisy-OR + decaying peak (`OBJECT_WEIGHT=0.25`,
`POSE_OOD=0.3`, `FALL=0.6`, `FALL_WINDOW_S=3.0`, `DECAY=0.9`); activities `ACTIVITY_NEAR_M`
(3D-дистанция людей), wrist-in-bbox контакт (object-major, `ContactClaim.beats`),
`seated_at_workstation` (upper+upright+stationary+workstation-класс рядом), `partially_in_frame`.

## Бенч: данные и протокол (общий субстрат всех актов)

**Сценарий = декларативный скрипт** (JSON): таймлайн сегментов на общем полу виртуальной камеры
175 см (та же, что LJ0–LJ3) + **ожидаемые события** с допусками по времени. Компилятор сценариев
`spike_pose/lj4_scenarios.py` собирает per-frame инжекцию из замороженных артефактов:

- **траектории/переходы** — из `mocap_tracks.npz` (walk/idle/cross, world-translation) и
  `mocap_transitions.npz` (sit_stand / lie_down / controlled_desc / fall, 60fps → субсэмпл 15fps);
- **позы** — кинематические истинные метки `y` (standing/sitting/lying) + conf; **лендмарки
  запястий** — из проекции 13 joints (для wrist-in-bbox контактов);
- **объекты** — синтетические статичные `ObjectState`-подобные записи (chair, keyboard, laptop,
  cup …) с bbox в кадре и классом из YOLO-словаря; появление/исчезновение задаёт сценарий;
- **инжекция** = поток per-frame наблюдений ПОСЛЕ детекторов: детекции тел (bbox+conf+identity
  по emitter'у), позы, запястья, объекты, pelvis3d (истина для E2-сравнения). Пиксельный слой
  честно вне охвата.

**Набор golden-сценариев (минимум, из плана):**

| id | сценарий | ожидаемые события (суть) |
|---|---|---|
| G1 | вошёл → сел → работает (клавиатура) | 1 трек; posture standing→sitting; `typing` start; anomaly=0 |
| G2 | встал → ушёл | `typing` end; posture→standing; трек исчезает; anomaly=0 |
| G3 | лёг (controlled lie-down) | posture→lying; **anomaly=0** (несущий негативный кейс) |
| G4 | упал | posture→lying быстро; **anomaly срабатывает** |
| G5 | двое встретились | 2 трека, без swap; `people_together` start/stop; anomaly=0 |
| G6 | (регрессия 15.3) один идёт | 1 трек, 0 фантомов, 0 ложных `people_together` |

**Эмиттер** — переиспользуем LJ3 (`lj3_bench.py`): **FLOOR** (чистая инжекция) и **STRESS**
(bursty-окклюзии, bbox-jitter, dropout, перемежающееся лицо; + для поз — флип метки по измеренной
confusion LJ1). Параметры фиксируются; сопоставим только внутри одного протокола.

**Метрики (реестр бенч-протокола, компонент «Симулятор/FSM»).**
- ведущая: **event-precision/recall** — совпадение журнальных событий (label + участники +
  start/stop в пределах допуска, учитывая dwell-лаг подтверждения) с ожидаемыми;
- **anomaly false-alarm rate** на нормальных сценариях (G1–G3, G5, G6) и **anomaly hit** на G4;
- доп.: journal-latency (задержка события vs истина; ожидаемо ≈ENTER_DWELL/EXIT_DWELL тиков),
  фантомные события (события, которых нет в сценарии, — по типам);
- CI: групповой bootstrap по прогону «сценарий × seed эмиттера» (N=1000, seed=0).

**Ground truth** — by construction: сценарий и есть истина.

## Акт S1 — Порт, битность, воспроизведение сценариев (несущий, гейт этапа)

**Цель.** Битный Python-порт `infer_activities`+`ActivityJournal`+`AnomalyScorer`
(`lj4_fusion.py`) с self-check против Rust-юнит-сценариев (минимум: 1-frame flicker не эмитится;
enter/exit dwell; cooling переживает YOLO-cadence гэп; churn-stitch выключен по умолчанию;
noisy-OR knife+fall; decaying peak; long-term lying ≠ fall). Затем baseline: полный стек
(lj3_tracker + lj4_fusion) на G1–G6, FLOOR и STRESS.

**Falsifiable-гипотеза S1.** *На FLOOR прод-стек воспроизводит все ожидаемые события сценариев
G1–G6 (event-P/R = 1.0 в пределах dwell-допусков) при нуле фантомных событий; под STRESS
деградация измерима и атрибутируема слою (трекер vs FSM vs raw-словарь) абляцией эмиттера.*

**Критерий провала (назван заранее).** Если на FLOOR (чистые данные, ноль детекторного шума)
события НЕ совпадают со сценарием — это либо дефект композиции слоёв (публикуем как находку —
симулятор для того и строился), либо непригодность словаря raw-activities к сценарию (кормит S3),
либо ошибка компилятора сценариев (чиним данные, не «подкручиваем» стек). Расхождение битности
порт↔Rust на self-check = стоп до починки порта; числа с небитного порта не публикуются.

## Акт S2 — Anomaly-гейт: тишина на норме, срабатывание на падении

**Цель.** Промерить продовое fall-правило anomaly против физики LJ2 на одном субстрате.

**Falsifiable-гипотеза S2.** *Продовый `AnomalyScorer` (standing→lying ≤ 3 с) даёт ложное
срабатывание на G3 (controlled lie-down быстрее окна) и/или пропуск на G4 (падение, размазанное
стрессом/окклюзией), тогда как правило E2 из LJ2 (пол: min pelvis ≤ 0.35 м И peak downward
velocity ≳ 1.13 м/с) на тех же прогонах разделяет G3/G4 чисто.*

**Критерий провала (назван заранее).** Если прод-правило на G3/G4 ведёт себя корректно (0 ложных,
G4 ловится) — честно публикуем «прод достаточен, E2 не нужен в 15.6» и снимаем contract-change из
плана порта. Если E2 на инжекции ведёт себя хуже прод-правила — фиксируем, что лабораторный порог
1.13 м/с не переносится на прод-сигналы (bbox/поза vs таз), и в 15.6 идёт прод-правило.
Обе развязки валидны; выбирается измерением, не нарративом.

*Замечание честности:* E2-порог откалиброван на stunt-падениях CMU (8 шт) → ограничивает
клинические падения сверху; в журнале повторяем caveat LJ2.

## Акт S3 — Аудит словаря raw-activities (вход для словаря v2)

**Цель.** Заменить «на глаз»-словарь измеренным: какие активности (а) подтверждаемы данными
(OpenImages VRD instances), (б) нужны golden-сценариям/потребителю журнала, (в) артефакты.

**Метод.**
1. Дотянуть `validation-annotations-vrd.csv` → посчитать per-predicate/per-object **инстансы**
   (не словарь): сколько реальных разметок у `holds`+keyboard/cup/book/phone, `at`+desk/table и т.д.
2. Сопоставить трём спискам: текущий MVM-словарь (6 контактных + 3 реляционных лейбла) ↔
   supervisable-предикаты инвентаря ↔ события, которые требуют сценарии G1–G6 и потребитель
   (journal/recap/LLM).
3. Вердикт-таблица словаря v2: keep / rename / drop / add, каждый ряд с числом инстансов
   или причиной («нужен сценарию», «не supervisable → CMU/фаза 16»).

**Falsifiable-гипотеза S3.** *Часть текущего словаря не подтверждаема данными (ноль/единицы
инстансов в VRD у соответствующего предикат×объект) и не требуется сценариями → кандидаты на drop;
при этом существуют предикаты с сотнями инстансов, которых в словаре нет (кандидаты add).*

**Критерий провала (назван заранее).** Если VRD-инстансы по всем текущим лейблам обильны и
маппинг чист — словарь оставляем, «артефактность» опровергнута измерением (несмотря на априорную
директиву — данные главнее). Если validation-VRD слишком мал для вердикта по редким предикатам —
честно помечаем «insufficient data», НЕ тянем train-VRD в этом этапе (перенос в фазу 16).

**Граница:** сам словарь v2 в код 15.4 не вносится — это решение для 15.6 (contract change
StateFile/MCP документируется там же, рядом с flexion).

## Гейт этапа 15.4 (сводно)

1. S1: битность порта подтверждена self-check'ами; на FLOOR event-P/R = 1.0 (в dwell-допусках),
   0 фантомных событий; STRESS-деградация измерена с CI и атрибутирована;
2. S2: anomaly false-alarm rate = 0 на G1–G3/G5/G6 и hit на G4 — хотя бы одной из двух конфигураций
   (прод-правило или E2), с явным вердиктом какая идёт в 15.6;
3. golden-сценарии зелёные в CI: Rust-runner (`--stub`-класс) прогоняет те же файлы сценариев через
   прод-крейты и ассертит контракт **текущего** прода (ассерты, которые чинит только словарь v2/E2,
   помечаются и переворачиваются в 15.6 — CI не ассертит то, чего прод ещё не обещает);
4. S3: вердикт-таблица словаря v2 с числами VRD-инстансов;
5. каждая цифра — из живого прогона, паспорт в `results/metrics.json["lj4"]`.

## Что это меняет в проде (мост к 15.6)

- Пакет порта 15.6 пополняется: fall-правило anomaly (вердикт S2), словарь raw-activities v2
  (вердикт S3, contract change), + уже решённые 15.1–15.3 (2D-GRIP/flexion/Mahalanobis,
  dwell+SL-вето, center-relink фикс).
- Golden-сценарии остаются в CI навсегда — регрессионная сетка для любого будущего рефакторинга
  temporal-стека (и приёмочный тест порта 15.6: Python-числа = Rust-числа на одних файлах).
- Head-on full-occlusion swap (наследство 15.3) характеризуется на G5-STRESS и фиксируется как
  known-limit с числом (решение — OCM/silhouette-cue — вне 15.4, кандидат в backlog 16+).

## Порядок исполнения

1. `spike_pose/lj4_fusion.py` — порт `infer_activities`+`ActivityJournal`+`AnomalyScorer`,
   self-check против Rust-юнит-сценариев (битность).
2. `spike_pose/lj4_scenarios.py` — компилятор сценариев (G1–G6 из mocap-артефактов + синтетические
   объекты) → `golden_scenarios.npz` + JSON-скрипты с ожидаемыми событиями.
3. S1: FLOOR/STRESS baseline, абляции по слоям, CI.
4. S2: прод-anomaly vs E2 на G3/G4 (+стресс-вариации).
5. S3: `validation-annotations-vrd.csv` → количественный аудит → вердикт-таблица словаря v2.
6. Rust CI-runner: `--stub`-класс тест в mvm workspace, читающий файлы сценариев (контракт
   текущего прода).
7. LJ4 (`notebooks/lj4/_build_lj4.py`), регистрация в `kctl.py`, датасет `mvm-golden-scenarios`
   (push-data → дождаться processing), push, Run-All, числа+паспорт → `results/metrics.json["lj4"]`.
